# bus-factor-from-git

[![check](https://github.com/sproshchaev/bus-factor-from-git/actions/workflows/check.yml/badge.svg)](https://github.com/sproshchaev/bus-factor-from-git/actions/workflows/check.yml)
[![License: MIT](https://img.shields.io/badge/License-MIT-blue.svg)](LICENSE)

Сколько людей должно уйти из проекта, чтобы половина кода осталась без автора? И какая доля кода уже сейчас ничья, потому что все, кто её писал, давно не коммитят?

Эксперимент к статье на Хабре: https://habr.com/ru/companies/otus/articles/1088904/

## Запуск

```bash
./run.sh
```

Нужен только Python, сторонних пакетов нет; проверено на 3.12 в CI и на 3.14 локально. Скрипт считает отчёт по готовым данным из `data/` и сверяет его с `expected.txt`. Если хоть одна цифра разошлась, код выхода 1.

Проверить сами данные можно так: `./fetch.sh` клонирует шесть проектов, выгружает историю на тех же коммитах и перезаписывает `data/`, после чего `git diff data/` должен быть пустым. В CI отчёт сверяется на каждый push (`check.yml`), а повторная выгрузка запускается, когда меняются `extract.py`, `fetch.sh`, `repos.txt` или `data/` (`data.yml`).

## Что здесь считается

**Автор файла** определяется по модели degree-of-authorship, как в работе Avelino и соавторов (ICPC 2016): учитывается, кто создал файл, сколько раз его менял и сколько правок внесли другие. Разработчик считается автором, если его нормированный DOA выше 0,75, а абсолютный не ниже 3,293.

**Truck factor** считается жадно: убираем автора с наибольшим числом файлов, пока оставшиеся авторы покрывают не меньше половины файлов. Число убранных и есть truck factor.

**Активный** разработчик коммитил в проект за последние 12 месяцев до зафиксированного коммита. «Truck factor среди активных» считается так же, но только по ним: ушедших git продолжает считать авторами, и обычный расчёт их учитывает.

**Ничьё сейчас** — доля файлов, у которых нет ни одного активного автора. **Ничьё, если уйдёт лидер** — то же самое после того, как из активных убран один человек с наибольшим числом файлов.

**Коммит с агентом** — коммит, в трейлере `Co-...-by:` которого стоит не человек, либо сделанный таким автором напрямую. Не человеком считается адрес вида `noreply@<домен>` вне `users.noreply.github.com` или имя и адрес со словом `agent`. Агенты и служебные боты (dependabot, renovate, github-actions) автором файла не становятся, а коммит с агентом засчитывается человеку, который его сделал.

## Чего этот расчёт не показывает

- Знание не равно авторству по git. Человек мог разобраться в модуле на ревью или на дежурстве и ни разу его не менять. Обратное тоже бывает: автор коммита с агентом мог не вчитываться в то, что принял.
- Truck factor открытого проекта и команды в компании — разные вещи. В открытых проектах много разовых участников, а в команде их нет, зато есть люди, которые ушли в соседний отдел и отвечают в чате.
- Сторонний код отсекается по расширению и по каталогам `vendor`, `node_modules`, `third_party`, `generated`, `build`, а не по Linguist, как в исходной работе. Псевдонимы склеиваются по общему адресу и по имени с отличием в одну букву.
- Детектор агентов ловит только тех, кто себя подписал. Код, принятый из чата без трейлера, неотличим от написанного руками. Правило грубое: служебная учётка с адресом `noreply@` (например, система переводов) будет принята за агента, а агент, который коммитит от учётки GitHub без слова `agent` и без трейлера, — за человека. На шести проектах из `repos.txt` все найденные агенты проверены вручную, людей среди них нет.

## Структура

```
bus_factor.py   расчёт отчёта по data/*.tsv
extract.py      выгрузка истории одного проекта в data/<имя>.tsv
fetch.sh        повторная выгрузка всех проектов по repos.txt
run.sh          отчёт и сверка с expected.txt
repos.txt       проекты и зафиксированные коммиты
expected.txt    эталонный отчёт
data/           готовые выгрузки, имена людей и пути файлов заменены номерами
```

В `data/` нет имён, адресов и путей: после склейки псевдонимов люди получают номера `d0001`, файлы — `f000001`. Для расчёта важна только их идентичность.
